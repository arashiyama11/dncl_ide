# 型情報追跡機能の実装計画

## 1. 概要

`language_server`に静的な型情報追跡機能を導入し、開発者体験を向上させることを目的とします。
この機能により、ホバー時の型情報表示や、将来的な型エラー検出などが可能になります。

## 2. 実装方針

開発は、和田卓人（@t_wada）氏が提唱するテスト駆動開発（TDD）のプロセスに厳密に従います。
具体的には、「レッド（失敗するテスト）→グリーン（テストをパスさせる最小限の実装）→リファクタリング（コードの改善）」のサイクルを徹底します。

型情報追跡は、以下のステップで段階的に実装します。

### ステップ1: 型推論エンジンの基礎構築

1. **`TypeInferenceVisitor`の作成**:
    * `AstVisitor`を参考に、ASTを巡回して型情報を推論するための`TypeInferenceVisitor`を新たに作成します。
    * このVisitorは、`SymbolTable`と連携し、各シンボルの型情報を解決・更新します。

2. **基本的な型の推論**:
    * リテラル（整数、浮動小数点、文字列、真偽値）から型を決定します。
    * 変数宣言時に、代入される式の型から変数の型を推論します。
    * `Symbol.type`フィールドに推論結果を格納します。

### ステップ2: `HoverService`との連携

1. **型情報の表示**:
    * `HoverService`を修正し、`AstInfoService`を通じて取得したシンボルの型情報をホバー時に表示するようにします。
    * 変数のホバー時には「変数: `varName` 型: `TypeName`」のように表示します。

### ステップ3: 複雑な型の推論

1. **配列型の推論**:
    * 配列リテラルの要素から、配列の型を推論します（例: `[1, 2, 3]` -> `Array<Int>`）。
    * 空の配列の扱いや、要素が混在する場合の型（例: `Array<Any>`）も考慮します。

2. **関数シグネチャの推論**:
    * 関数のパラメータと戻り値の型を推論します。
    * `戻り値`キーワードから戻り値の型を特定します。
    * 関数シンボルには、`(引数型) -> 戻り値型`のような形式で型情報を格納します。

3. **組み込み関数の型定義**:
    * `AllBuiltInFunction`に、各組み込み関数のシグネチャ（引数と戻り値の型）を定義します。
    * これにより、組み込み関数呼び出し時の型チェックと推論が正確になります。

### ステップ4: 型エラーの診断（将来的な展望）

1. **`DiagnosticService`との連携**:
    * 型推論エンジンが型の不一致を検出した場合（例: `整数`型の変数に`文字列`を代入）、
      `DiagnosticService`にエラー情報を通知します。
    * エディタ上で型エラーが波線で表示されるようになります。

## 3. 関連する主要コンポーネント

* **`AstVisitor.kt`**: 型推論ビジターのベースとなります。
* **`SymbolTable.kt`**: シンボル情報（型情報を含む）を管理します。
* **`HoverService.kt`**: 型情報をユーザーに提示します。
* **`AstInfoService.kt`**: ASTとシンボルテーブルを管理し、型推論の実行をトリガーします。
* **`DiagnosticService.kt`**: 型エラーを報告します。

## 4. 開発マイルストーン

実装が完了した項目にはチェックを入れます（`[ ]` -> `[x]`）。

- [ ] **M1: 基本的な型推論とホバー表示**
    - [ ] `TypeInferenceVisitor`の雛形を作成。
    - [ ] 整数、浮動小数点、文字列、真偽値の型推論を実装。
    - [ ] `HoverService`で型情報を表示。
- [ ] **M2: 配列型と関数型の推論**
    - [ ] 配列リテラルと関数定義の型推論を実装。
    - [ ] 組み込み関数の型シグネチャを定義。
- [ ] **M3: 型エラーの検出**
    - [ ] 基本的な型エラー（代入時の不一致など）を検出し、`DiagnosticService`に報告する機能を実装。
