# DNCL Language Server (LSP) TODOリスト

このドキュメントは、`DNCLLanguageServer.kt` における既存のLSP機能の実装状況を評価し、今後の改善点や未実装の機能をまとめたものです。

## 1. 実装が薄い、または簡易的な機能

以下の機能は基本的な動作はするものの、より堅牢な実装や高度な機能追加が必要です。

### 1.1 `textDocument/hover` (Hover機能)
- **現状**: `builtInFunctionDescriptions` に基づく組み込み関数の説明のみを提供。
- **課題**: ユーザー定義の変数、関数、型などに対するホバー情報を提供できていない。より詳細な型情報やドキュメントコメントの表示に対応する必要がある。
- **改善案**: 構文解析結果（ASTやシンボルテーブル）を利用して、カーソル位置のシンボルに対応する定義元や型情報を取得し、ホバーとして表示する。

### 1.2 `textDocument/definition` (Go to Definition機能)
- **現状**: `SuggestionUseCase` を利用し、コード内のリテラルとオフセットに基づいて定義元を推測している。
- **課題**: 単純なリテラルマッチングに近く、スコープやセマンティクスを考慮した正確な定義元へのジャンプができていない可能性がある。特に、同名の異なるスコープのシンボルや、複雑なデータ構造内の定義に対応できていない。
- **改善案**: 構文解析結果からシンボルテーブルを構築し、カーソル位置のシンボルがどの定義に対応するかを正確に解決する。

### 1.3 `textDocument/references` (Find References機能)
- **現状**: `Lexer` を利用し、対象トークンのリテラルと一致するすべてのトークンを検索している。
- **課題**: テキストベースの単純な検索であり、セマンティックな参照（スコープ、型、異なる定義だが同じリテラルを持つものなど）を区別できていない。
- **改善案**: シンボルテーブルとASTを利用して、対象シンボルのすべての参照箇所をセマンティックに特定する。

### 1.4 `textDocument/rename` (Rename Symbol機能)
- **現状**: `Lexer` を利用し、対象トークンのリテラルと一致するすべてのトークンを新しい名前に置換している。
- **課題**: `textDocument/references` と同様に、テキストベースの置換であり、セマンティックなリネームではない。これにより、意図しない箇所がリネームされたり、リネームすべき箇所が漏れたりする可能性がある。
- **改善案**: `textDocument/references` のセマンティックな参照解決を利用し、正確な参照箇所のみをリネームする。

### 1.5 `textDocument/formatting` (Formatting機能)
- **現状**: 各行の先頭と末尾の空白をトリムするだけの非常に簡易的な実装。
- **課題**: DNCLのコードスタイルガイド（もしあれば）に沿った整形や、インデントの自動調整、空白の追加・削除など、本格的なフォーマット機能が欠けている。
- **改善案**: ASTを走査し、DNCLの構文構造に基づいてコードを再構築・整形する。

### 1.6 `textDocument/codeAction` (Code Action / Quick Fix機能)
- **現状**: 「未定義の識別子」に対する「表示」のクイックフィックスのみを提供。
- **課題**: 提供されるコードアクションの種類が非常に限定的。より多様なエラーや警告に対するクイックフィックス、リファクタリング候補などを提供できる。
- **改善案**: 診断結果やカーソル位置のコンテキストに基づいて、より多くのコードアクション（例: 変数抽出、関数抽出、未使用インポートの削除など）を実装する。

### 1.7 `textDocument/semanticTokens/full` (Semantic Tokens機能)
- **現状**: `getTokenType` 関数が基本的なトークンタイプ（キーワード、変数、数値、文字列、コメント、演算子）に分類している。
- **課題**: 変数と関数、グローバルとローカルなど、より詳細なセマンティックな分類ができていない。これにより、エディタでのよりリッチなシンタックスハイライトが制限される。
- **改善案**: 構文解析結果やシンボルテーブルを利用して、より粒度の細かいトークンタイプ（例: 関数名、パラメータ、クラス名、型名など）を識別し、LSPのセマンティックトークン仕様に沿って提供する。

## 2. 未実装または不明確な機能

### 2.1 Server実装の明確化
- **現状**: `PLAN.md` の「フェーズ4: Server実装」は完了とされているが、`DNCLLanguageServer.kt` はLSPのコアロジックのみを担っており、HTTP/WebSocketサーバーとしての起動機能はコードベースから明確に確認できない。`Main.kt` がコメントアウトされている。
- **課題**: LSPサーバーをどのように起動し、クライアントと通信するのかの全体像が不明確。
- **改善案**:
    - Ktorなどを用いて、LSPプロトコルを介した通信を可能にするHTTP/WebSocketサーバーを実装する。
    - スタンドアロンのLSPサーバーとして起動するための明確なエントリポイント（例: `Main.kt` の再活性化または新規作成）を確立する。
    - `Main.kt` がコメントアウトされている理由と、その意図（例: composeAppからの直接呼び出しのみを想定しているのか、将来的なスタンドアロンサーバーの計画があるのか）を確認し、`PLAN.md` に追記する。

## 3. その他
- **エラーハンドリングの強化**: 現在の`handleMessage`内の`try-catch`は汎用的。LSPのエラーコードに合わせたより詳細なエラーハンドリングを検討する。
- **テストカバレッジの向上**: 上記の各機能について、より網羅的なユニットテストおよび統合テストを追加する。
- **パフォーマンス最適化**: 大規模なファイルや頻繁な変更に対するパフォーマンス（特に`textDocument/didChange`や`publishDiagnostics`）を評価し、必要に応じて最適化（例: 差分解析、キャッシュ機構の導入）を行う。
